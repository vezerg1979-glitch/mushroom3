# Публикация в RuStore

Пошагово: от ключа подписи до карточки приложения. Всё, что можно было
автоматизировать, вынесено в `.github/workflows/build-release.yml`; здесь
остаётся то, что делается руками один раз.

## 1. Ключ подписи

Магазин принимает только подписанные сборки. Ключ создаётся один раз и живёт
дальше вечно: потеряете — обновить приложение в магазине будет нельзя, только
publish заново под другим именем пакета.

```bash
keytool -genkey -v -keystore mushroom-release.keystore \
  -alias mushroom -keyalg RSA -keysize 4096 -validity 10000
```

Ответы на вопросы можно давать любые осмысленные; пароль запишите отдельно.
Срок 10000 дней взят не случайно: магазины требуют ключ, действительный
минимум до 2033 года.

**Храните файл вне репозитория.** В git его класть нельзя даже в приватный:
любой, кто получит доступ, сможет выпускать обновления от вашего имени.

## 2. Ключ в секреты GitHub

```bash
base64 -w0 mushroom-release.keystore > keystore.b64
```

На Windows в PowerShell:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("mushroom-release.keystore")) > keystore.b64
```

Дальше в репозитории: **Settings → Secrets and variables → Actions → New
repository secret**, и создать четыре штуки:

| Имя | Значение |
|---|---|
| `KEYSTORE_BASE64` | содержимое `keystore.b64` целиком, одной строкой |
| `KEYSTORE_PASSWORD` | пароль хранилища |
| `KEY_ALIAS` | `mushroom` |
| `KEY_PASSWORD` | пароль ключа (обычно тот же) |

## 3. Сборка релиза

Если собираете у себя, а не в облаке, — пошагово в `docs/release-local.md`.
Ниже про сборку в GitHub Actions.

Вкладка **Actions → build-release → Run workflow**. Либо по тегу:

```bash
git tag v2.7 && git push origin v2.7
```

Workflow сначала прогоняет тесты и только потом собирает — подписанный APK
с несобирающейся моделью никому не нужен. Готовый файл в разделе Artifacts.

Перед каждой новой загрузкой поднимайте `android.numeric_version` в
`buildozer.spec`: магазин отвергает сборку с тем же или меньшим кодом версии.
Схема простая — 2.7 это 20700, 2.7.1 будет 20701, 2.8 будет 20800.

## 4. Что потребует магазин

**Возрастная категория.** 0+, приложение не содержит ничего спорного.

**Категория.** «Путешествия» или «Погода» — подходят обе.

**Политика конфиденциальности и условия использования.** Обязательны — первая
потому, что приложение просит геолокацию, вторые появились вместе с платной
разблокировкой рекламы. С версии 3.0 оба документа встроены прямо в
приложение (текст в `android/legal.py`, кнопки на экране покупки «без
рекламы» открывают их всплывающим окном) — ссылка на GitHub для этого не
нужна, репозиторий используется только для сборки. `docs/privacy.md` и
`docs/terms.md` рядом — исходный, человекочитаемый вариант тех же текстов
для правки; при изменении политики нужно поправить оба места руками, `.md`
для истории и `legal.py` для показа в приложении, автосинхронизации между
ними нет. Если магазин при модерации всё же попросит именно веб-ссылку —
проще всего один раз включить GitHub Pages в настройках репозитория.

**Скриншоты.** Минимум два, в формате телефона. Готовые лежат в `android/`:
`screenshot.png`, `screenshot-map.png`, `screenshot-walk.png`,
`screenshot-detail.png`.

**Иконка.** 512×512 — `android/icon.png`. В ней намеренно нет подписи: на
рабочем столе телефона значок занимает 48 dp, надпись там не читается и
только отъедает площадь у картинки. Название приложение получает от системы,
из `buildozer.spec`. Мелкая копия для карточки магазина — `android/icon-192.png`,
она собирается из того же файла (`make_icons.py`), и тест не даёт им разъехаться.

**Описание.** Заготовка в конце этого файла.

## 5. Обоснование разрешений

Модерация спрашивает, зачем приложению фоновая геолокация. Ответ по существу:

> Приложение записывает маршрут прогулки по лесу, чтобы показать пройденное
> расстояние и вывести пользователя обратно к точке старта. Запись должна
> продолжаться с погашенным экраном — телефон лежит в кармане, пока человек
> собирает грибы. Координаты хранятся только на устройстве и никуда не
> передаются.

Последнее предложение — правда, и это стоит проверять при каждом изменении
кода: `track.py` и `tracklog.py` пишут исключительно в локальные файлы.

## 6. Про targetSdk и фоновый сервис

Сейчас в профиле магазина стоит `android.api = 33`, и это осознанное решение,
а не недосмотр. На `34` (Android 14) система требует, чтобы у фонового сервиса
в манифесте был атрибут `android:foregroundServiceType="location"`, иначе
сервис падает при старте с `MissingForegroundServiceTypeException`.
python-for-android версии 2024.01.21 этот атрибут не выставляет.

Если RuStore потребует targetSdk 34 или выше, есть три пути:

1. Обновить p4a до версии, где поддержка появилась, и заново пройти всю
   цепочку совместимости (Python, Cython, Kivy) — это полдня работы и риск
   вернуться к падениям, которые описаны в `android/README.md`.
2. Пропатчить шаблон манифеста в p4a перед сборкой — быстро, но патч придётся
   тащить за собой в каждый прогон CI.
3. Отказаться от фоновой записи: трек пишется только с открытым экраном.
   Приложение при этом остаётся полезным, теряется удобство.

Требования магазинов меняются, поэтому перед публикацией проверьте актуальное
на `https://www.rustore.ru/help/developers/` — сведения здесь могут устареть.

## 7. Реклама и покупка «без рекламы»

Раньше здесь стояла кнопка «♥» с добровольным переводом. Сейчас вместо неё
на главном экране — «Без рекламы»: показ рекламы Яндекса и разовая покупка
за 300 руб., которая её выключает. Это не косметическая замена, а смена
сути, и у неё другие последствия для публикации.

**Это уже не пожертвование, а продажа функциональности.** Раздел ниже в
старой версии документа опирался на то, что перевод ничего не разблокирует.
Теперь разблокирует — рекламу. Большинство магазинов, включая RuStore,
требуют для таких покупок встроенный биллинг, а не перевод по номеру
телефона в обход магазина. Пока `billing.py` не подключён по-настоящему
(см. ниже), единственный работающий способ купить — код разблокировки по
СБП-переводу, `licensecode.py`. Держать его на витрине магазина как
единственный способ оплаты — риск для прохождения модерации; проверьте
актуальные правила RuStore, прежде чем публиковать сборку с этой кнопкой в
таком виде. Как временная мера подходит лучше, чем ничего, но не как
постоянное решение.

**Реклама — Яндекс Реклама, и код в `android/ads.py` не проверен на
реальном показе.** Класс, метод и константы там помечены «СВЕРИТЬ» — я
собирал их по общей форме API, без доступа к текущей документации и без
телефона, на котором это можно было бы прогнать. Перед сборкой:

* зарегистрируйте приложение в кабинете Яндекс Рекламы, получите свой
  `AD_UNIT_ID` и впишите его вместо плейсхолдера;
* сверьте имена классов (`BannerAdView`, `BannerAdSize`, `AdRequest`,
  `MobileAds`) с документацией https://yandex.ru/dev/mobile-ads/doc/ru/android/quick-start —
  SDK меняется версия к версии, и то, что здесь написано, могло устареть
  уже на момент, когда вы это читаете;
* добавьте зависимость SDK в сборку — `requirements = ...` в
  `buildozer.spec` для этого не годится, это нативная Java/Kotlin-
  библиотека, а не pip-пакет; понадобится gradle-зависимость через
  p4a-рецепт или ручную правку сборки;
* проверьте на настоящем телефоне. Без реального показа рекламы нельзя
  сказать, работает ли это вообще.

**Полноэкранная реклама — myTarget, `android/interstitial.py`, надёжнее
`ads.py`, но тоже не проверена на реальном показе.** Класс, методы
слушателя и их JNI-сигнатуры взяты дословно из документации, которую
предоставили при подключении, а не собраны по общей форме API вслепую —
это ощутимо снижает риск, но не отменяет прогон на телефоне перед
сборкой. Перед сборкой:

* slotId уже вписан (`SLOT_ID = 2056349` в `interstitial.py`) — если
  заводили другой блок под другое приложение, проверьте, что это тот
  самый;
* добавьте зависимость myTarget SDK в сборку — тот же вопрос, что и с
  Яндекс Рекламой выше: нативная Java-библиотека, gradle-зависимость
  через p4a-рецепт, а не `requirements` в `buildozer.spec`;
* проверьте на настоящем телефоне, что `onLoad`/`onNoAd` действительно
  приходят и полноэкранное объявление открывается и закрывается штатно —
  фейковая среда для тестов (`tests/androidfake.py`) проверяет только то,
  что код доходит до конца без опечаток в именах и числе аргументов, а не
  то, что реклама реально показалась.

**RuStore-биллинг сегодня не работает, и `billing.is_available()` честно
отвечает `False`.** Часть публичного API RuStore Billing SDK — это
Kotlin-корутины, а не обычные Java-методы, и вызвать их через jnius нельзя
без дополнительного класса-моста, который нужно написать и скомпилировать
отдельно (см. подробности в docstring `android/billing.py`). Пока это не
сделано и не проверено на телефоне с настоящей покупкой из песочницы
RuStore, кнопка «Купить через RuStore» в приложении не появляется вовсе —
`premium_screen.py` показывает только рабочий путь по коду разблокировки.

Что стоит проверить и сделать перед подачей на модерацию:

* Товар «без рекламы» заведён в консоли RuStore, `PRODUCT_ID` в
  `billing.py` совпадает с тем, что там указано.
* RuStore Billing SDK подключён как gradle-зависимость (тот же вопрос, что
  и с рекламой выше — нужен p4a-рецепт).
* Приём переводов от физических лиц по СБП — это доход. Статус
  самозанятого решает вопрос с налогами и стоит недорого; актуально, пока
  код разблокировки остаётся рабочим путём оплаты.
* Реквизиты для ручного пути задаются в `android/donate.py`, как и раньше:
  `SBP_PHONE`, `SBP_BANK`, `SBP_LINK`. Платёжная ссылка — то же самое, что
  зашито в QR банка, кнопка ведёт сразу на экран перевода. Допустимые хосты
  перечислены в `PAY_HOSTS`.
* Секретный ключ в `android/licensecode.py` (`SECRET`) обязательно
  заменить перед первой публикацией — команда в комментарии над
  константой. Значение по умолчанию — сплошные нули, тест
  `test_default_secret_is_a_visible_placeholder` следит, чтобы это было
  видно с первого взгляда, а не потерялось в диффе. Заменённый ключ
  храните только у себя: он и есть весь смысл кода разблокировки, а его
  утечка означает, что код сможет посчитать кто угодно.
* Код разблокировки для конкретного покупателя считается инструментом
  `tools/make_unlock_code.py device_code` — запускать у себя, после того
  как деньги пришли.
* Это не защита от списывания, и `premium_screen.py` говорит об этом
  человеку прямо, а не молчит: секрет живёт в самом APK, а Python из него
  достать легче, чем скомпилированный Java-код. Настоящую защиту от
  списывания даёт только RuStore-биллинг, когда его доведут до конца.

## Заготовка описания для карточки

**Название:**

> Навигатор грибника

Имя пакета при этом остаётся прежним — `ru.grezev.mushroomforecast`. Менять
его нельзя: для магазина и для Android это другое приложение, обновление
поверх установленного не встанет, а журнал, треки и снимки у людей останутся
в старом. Название в карточке и на экране телефона меняется свободно.

**Короткое описание (до 80 символов):**

> Прогноз грибного слоя, маршрут и путь обратно — карта работает без сети

**Полное описание:**

> Это приложение я делал для себя. Ходить с ним в лес оказалось настолько
> спокойнее, что я решил им поделиться: польза здесь не только грибная.
> Карта, маршрут и стрелка к машине работают без сети, и человек, который
> в лесу теряется, в любой момент видит, где он и как выйти обратно.
>
> Приложение считает, когда пойдут грибы, по данным о погоде за прошедший
> месяц и прогнозу на две недели вперёд.
>
> Что показывает:
>
> • Индекс плодоношения на 16 дней вперёд, отдельно по десяти видам:
>   белый, подберёзовик, подосиновик, лисичка, маслёнок, опёнок, груздь,
>   сыроежка, вешенка, сморчок.
> • Разбор каждого дня: почему прогноз именно такой и что мешает —
>   сухая подстилка, холодная почва, жара или заморозок.
> • Несколько сохранённых мест с их собственными прогнозами.
>
> В лесу:
>
> • Запись маршрута с подсчётом пройденного расстояния.
> • Метки находок с указанием вида и количества.
> • Возврат к машине: стрелка с направлением и расстоянием.
> • Прошлые походы на карте: маршруты блёклыми линиями, точками — места,
>   где вы брали, с видом и количеством. Поход строится по своим местам.
> • Время до заката и предупреждение о разряде: телефон в лесу — это ещё
>   и дорога обратно.
> • Карта работает без сети, если заранее скачать район.
>
> Как считается прогноз. Влага лесной подстилки моделируется как резервуар,
> который пополняют дожди и опустошает испарение. Температура почвы получается
> сглаживанием температуры воздуха с задержкой в несколько суток. Плодоношение
> — реакция на событие увлажнения, а не на ровную сырость, поэтому после
> ливня будет волна, а под непрерывной моросью только умеренный фон.
> Заложенное сегодня выходит на поверхность через 3–16 суток в зависимости
> от вида.
>
> Чего приложение не умеет: оно не знает ваш лес, тип почвы и состояние
> мицелия. Это оценка шансов по погоде, а не гарантия.
>
> Данные о погоде — сервис Open-Meteo (лицензия CC-BY). Карта —
> OpenStreetMap. Координаты маршрута хранятся только на вашем телефоне.

## Если сборка встала на тестах

Сначала посмотрите, какой текст ошибки. `No such file or directory:
'…/../android'` — это старый способ поиска исходников, который зависел от
рабочего каталога; в нынешнем коде такой строки нет вовсе. Значит, собирается
не тот коммит: проверьте, что архив распакован поверх репозитория и изменения
закоммичены и отправлены.

Проверить у себя, ничего не собирая:

```bash
cd /tmp && python -m pytest /путь/к/проекту/tests -q
```

Если отсюда тесты проходят, пути в порядке — они больше не зависят от того,
откуда их запустили. Ту же проверку делает CI шагом «Прогон из чужого
каталога».

### «grep: release.log: No such file or directory»

Это не поломка сборки, а шаг разбора лога, который запустился, когда сборки
не было. Он стоит с `if: always()` — нужен-то он именно при падении, — но
`always()` означает и «когда до сборки не дошли»: если раньше споткнулись
тесты, шаг всё равно запускался, лога не находил и падал сам. Красным горел
он, а настоящая причина уезжала вверх по журналу.

Теперь шаг проверяет наличие лога и честно пишет «до сборки дело не дошло,
смотрите шаг, который упал раньше». Красным остаётся тот шаг, который
действительно сломался.

### «No such file or directory: …/../android» на сборе тестов

В корне проекта завелись копии файлов тестов — остатки старой раскладки.
Голый `pytest -q`, которым идёт проверка перед релизом, собирал их наравне с
настоящими из `tests/`, а копии отстали на несколько правок и падали ещё до
первой проверки.

Что делать:

```bash
git ls-files 'test_*.py' 'smoke_ui_test.py' | grep -v '^tests/'
git rm test_icons.py test_module_api.py      # то, что нашлось
```

Файл `pytest.ini` в корне (`testpaths = tests`) больше не даёт таким копиям
попадать в сбор, а тест `test_no_stray_copies_of_tests_outside_the_tests_folder`
называет их по именам — молчать о них нельзя, иначе человек будет править
файл, который никто не исполняет.

### «ModuleNotFoundError: No module named 'kivy'» на сборе тестов

Проверка перед релизом идёт в образе buildozer, где Kivy нет. Дымовой файл
`tests/smoke_ui_test.py` окна поднимает по-настоящему и без Kivy пропускается
целиком — но пропуск работает, только если pytest успел файл собрать. Импорт
Kivy на верхнем уровне ломает именно сбор, а падение на сборе прекращает весь
прогон.

Что должно спасать теперь, даже если такой импорт снова кто-то напишет:

* `tests/conftest.py` не отдаёт этот файл на сбор, когда Kivy не установлен;
* `test_no_test_imports_kivy_before_the_skip` называет файл и строку;
* шаг «Тесты без Kivy» в tests.yml прогоняет набор без Kivy на каждом коммите.

Если ошибка всё же в логе — сверьте, тот ли коммит собирается: в исправленной
версии на 29-й строке `smoke_ui_test.py` стоит комментарий, а не импорт.

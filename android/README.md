# Навигатор грибника — сборка APK

Состав проекта:

| Файл | Назначение |
|---|---|
| `main.py` | мобильный интерфейс на Kivy (точка входа для Android) |
| `mushroom_forecast.py` | расчётное ядро: водный баланс, температура почвы, индекс по видам |
| `atlas.py` | эталонные изображения грибов и признаки видов |
| `survival.py` | разрывы фоновой записи и подсказки по настройкам производителей |
| `backup.py`, `backupscreen.py` | резервная копия наблюдений: архив, передача системе, восстановление |
| `assets/species/` | необязательные свои фотографии видов (`<slug>.jpg`), заменяют рисунок |
| `icon.png`, `icon-192.png`, `presplash.png` | значок и заставка; собираются из `tools/icon-source.jpg` скриптом `tools/make_icons.py` |
| `buildozer.spec` | конфигурация сборки |
| `build-apk.yml` | сборка в GitHub Actions (положить в `.github/workflows/`) |

Погодные данные — Open-Meteo, без ключа, требуется интернет при обновлении прогноза.

---

## Вариант 1. Сборка в облаке GitHub Actions (ничего ставить не нужно)

1. Создать репозиторий на GitHub, залить туда `main.py`, `mushroom_forecast.py`, `buildozer.spec`.
2. Файл `build-apk.yml` положить по пути `.github/workflows/build-apk.yml`.
3. Вкладка **Actions → build-apk → Run workflow**.
4. Первая сборка идёт 30–40 минут (качается Android SDK/NDK, компилируется CPython
   под ARM), последующие — около 10 минут за счёт кэша.
5. На странице запуска, раздел **Artifacts**, скачать `mushroom-apk` →
   внутри `mushroomforecast-1.0-arm64-v8a_armeabi-v7a-debug.apk`.
6. Перекинуть на телефон, разрешить установку из неизвестных источников, поставить.

Это debug-сборка: она подписана отладочным ключом, ставится и работает нормально,
но в Google Play её не выложить. Для релиза нужен свой keystore и `buildozer android release`.

## Вариант 2. Локальная сборка (Linux или WSL2 на Windows)

Buildozer под чистой Windows не работает — только WSL2/Linux/macOS.

```bash
sudo apt update && sudo apt install -y git zip unzip openjdk-17-jdk python3-pip \
    autoconf libtool pkg-config zlib1g-dev libncurses-dev libtinfo6 cmake \
    libffi-dev libssl-dev build-essential ccache
pip install --user buildozer cython==0.29.36

cd android
buildozer -v android debug        # результат в bin/*.apk
buildozer android debug deploy run logcat   # если телефон подключён по USB с отладкой
```

## Вариант 3. Проверка интерфейса на ПК до сборки

```bash
pip install kivy certifi
python main.py
```

## Настройка

* **Значок и заставка.** Положить рядом `icon.png` (512×512) и `presplash.png`,
  раскомментировать соответствующие строки в `buildozer.spec`.
* **Версия.** Поле `version` в `buildozer.spec`.
* **Калибровка модели.** Константы `CAPACITY_MM`, `CANOPY`, `BASE`, `GAIN` в начале
  `mushroom_forecast.py`; профили видов — словарь `SPECIES` там же.
* **Место по умолчанию.** Значение `text=` у поля ввода в `main.py`
  (сейчас Душоново). Можно вводить и координаты: `56.02, 38.28`.

## Известные ограничения

* Прогноз требует сети; офлайн-кэша последнего расчёта пока нет —
  при необходимости легко добавить сохранение JSON в `App.user_data_dir`.
* Уведомление «сегодня выход грибов» потребует Android-сервиса
  (`services` в `buildozer.spec` + `plyer.notification`).
* Модель эвристическая и калибровалась по литературным представлениям о сроках
  слоёв, а не по вашим наблюдениям. Журнал выездов позволил бы подогнать
  параметры по МНК.

## Рабочая конфигурация сборки (не менять вслепую)

Комбинация ниже получена отладкой полутора десятков прогонов CI. Каждый пункт
решает конкретную поломку, воспроизводимую при откате:

| Что | Значение | Зачем |
|---|---|---|
| `android/filetype.py` | заглушка | Kivy 2.3.1 делает `import filetype` при импорте графики; без файла приложение падает на старте с `ModuleNotFoundError`, показывая только заставку «Loading» |
| `requirements` | `python3,kivy==2.3.1,certifi,openssl` | `urllib3` и `plyer` не используются кодом и ломают сборку; сам `filetype` с PyPI не ставится — рецепта у p4a нет |
| `android.ndk` | `25b` | на r28c python-for-android собирает Python 3.14, несовместимый с Cython 0.29 и Kivy 2.3.1 |
| `android.ndk_api` | `24` | при 21 у r25b не хватает заголовков, обрыв на этапе `create` |
| `android.archs` | `arm64-v8a` | все актуальные телефоны 64-битные, сборка вдвое быстрее |
| CI | `ArtemSBulgakov/buildozer-action@v1` | Java, Gradle, SDK и NDK зафиксированы в образе; ручная сборка на раннере ломается при каждом обновлении окружения GitHub |

Отладка при чёрном экране после установки: `adb logcat -s python` покажет
traceback. Именно так была найдена причина с `filetype` — за один прогон,
после десятка слепых попыток.

## Навигация для грибника

Три новых модуля, каждый со своей зоной ответственности:

| Файл | Что делает |
|---|---|
| `nav.py` | арифметика: азимут, расстояние, курс движения, словесные подсказки. Ни Kivy, ни Android — целиком покрыт тестами |
| `navwidget.py` | стрелка на экране: только рисование, все числа приходят готовыми |
| `tiles.py` | предзагрузка карты в тот же кэш, что использует `mapview` |

**Откуда берётся направление.** Компас под пологом леса врёт, поэтому основной
источник — курс движения по хвосту трека (`course_over_ground`). Пока человек
идёт, подсказка относительная: «↑ прямо», «→ направо». Если стоит, курса нет,
и показывается абсолютный азимут: «на северо-восток, 740 м».

**Почему по четырём точкам, а не по двум.** Пара соседних точек даёт направление,
скачущее на десятки градусов даже при ровной ходьбе — отсюда `COURSE_SPAN = 4`.

**Офлайн-карта.** `tiles.plan()` считает список клеток, `estimate()` — объём и
время ДО начала загрузки, `download()` качает в фоне с паузами, щадящими сервер
OSM. Радиус ограничен пятью километрами: массовую выкачку OSM вправе заблокировать.

## Что чинилось в записи трека

**Симптом:** GPS работает, точка на карте видна, а линия маршрута не рисуется.

**Причина:** под пологом леса приёмник рапортует точность 60–80 м, а фильтр
в `track.py` отбрасывал всё хуже 50 м. Отбрасывались все точки подряд, трек
оставался пустым, и понять это было нельзя — положение-то показывалось.

**Что сделано.** После пяти отброшенных подряд точек порог временно
поднимается до 150 м (`FALLBACK_ACCURACY_M`): грубая линия лучше её
отсутствия. Такие точки считаются в `Walk.rough`, а `Walk.signal_state()`
пишет об этом в подсказке. Одна записанная точка теперь рисуется кружком —
раньше при `len(points) == 1` не было видно ничего.

## Компас

`compass.py` — курс телефона по магнитометру и акселерометру. Нужен потому,
что курс по треку (`nav.course_over_ground`) существует только при движении:
остановился — стрелка замёрзла.

Тонкости, из-за которых компасы обычно врут и которые здесь учтены: наклон
телефона (без поправки ошибка достигает десятков градусов), магнитное
склонение (для Подмосковья +11°, иначе на километре набегают сотни метров
вбок), переход через север при сглаживании (наивное среднее 359° и 1° даёт
180°) и почти вертикальное положение, когда горизонтальная проекция
вырождается и показаниям верить нельзя.

## Походы в журнал

`walk2journal.py` переносит находки в `journal.csv`, по которому
`calibrate.py` подгоняет модель. Обилие 0–5 считается по плотности находок на
километр маршрута: пять белых на километр и на десять — разные события.
Пустой выход записывается тоже, иначе модель обучится только на удачных днях.

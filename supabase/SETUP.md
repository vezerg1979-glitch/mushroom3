# Подключение общего альбома (Supabase)

Личный фотодневник работает **без Supabase**. Для обмена фотографиями один владелец приложения создаёт и оплачивает при необходимости **общий проект Supabase для ВСЕХ пользователей**. Не просите пользователей создавать личные проекты: для общей галереи все экземпляры APK должны быть собраны с одним и тем же URL проекта и publishable/anon key. Это **не секреты**; они видны в APK. **Никогда не добавляйте `service_role`/secret key в приложение или репозиторий.**

1. Создайте Supabase-проект. В **Authentication → Providers → Anonymous Sign-Ins** включите анонимный вход. Перед публичным запуском включите CAPTCHA/anti-bot для анонимной регистрации и настройте лимиты проекта.
2. Откройте **SQL Editor** и выполните весь файл [`setup.sql`](setup.sql) один раз. Он создаёт таблицу карточек, таблицу жалоб, **private**-хранилище фотографий и RLS. При повторном запуске политики выдадут ошибку «already exists»; не выполняйте файл повторно поверх существующего проекта.
3. В **Project Settings → API** найдите HTTPS `Project URL` и **publishable key** (`sb_publishable_...`) или старый `anon` JWT (не `service_role`). Проверьте в тестовом APK, что ключ принимает запросы к `/auth/v1/signup`. В GitHub: **Settings → Secrets and variables → Actions → New repository secret**: добавьте `SUPABASE_URL` и `SUPABASE_ANON_KEY`. После этого запускайте сборку Android APK через Actions. Эти значения встроятся в конкретный APK; изменение секретов без новой сборки не поменяет уже установленное приложение.
4. Для локальной сборки создайте **не коммитя** файл `supabase.properties` в корне проекта:

```properties
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
```

5. Добавьте 1–2 тестовых фотографии в Android-приложении, отправьте их в общий альбом. Новые записи имеют `status='pending'`. **Ничего не публикуется автоматически**. Владельцу проекта необходимо регулярно проверять очередь: в **Supabase → Table Editor → garden_photos** найдите `pending`, посмотрите изображение в **Storage → garden-photos**, убедитесь, что нет людей, чужих изображений, контактов, адресов или небезопасного контента. Затем в SQL Editor выполните только для проверенного ID:

```sql
update public.garden_photos set status = 'approved'
where id = 'UUID_ПРОВЕРЕННОГО_ФОТО' and status = 'pending';
```

Для отказа установите `status='rejected'`, затем удалите запрещённый файл из Storage. Для жалоб проверяйте `garden_reports` и скрывайте проблемную публикацию сменой `status='rejected'`; при необходимости удаляйте файл. Другие пользователи не могут читать ожидающие или отклонённые фото через RLS. Изображения выдаются через временные подписанные URL после проверки прав.

## Важно до публичного запуска

- Не публикуйте приложение с общим альбомом, пока не назначен реальный модератор, не настроены лимиты/anti-bot и не проверены настройки приватного bucket и RLS на двух разных телефонах/учётных записях.
- Анонимный аккаунт сохраняется **только на устройстве**; после очистки данных/переустановки возможна потеря доступа к удалению старых публикаций. Владелец сервиса должен обеспечить контакт для запросов на удаление и политику хранения/удаления данных.
- Личное название растения, расположение куста, дата посадки и заметки **не отправляются**; при публикации передаются только очищенный от EXIF JPEG, псевдоним, сорт и описание. Если адрес/лицо видны прямо на фото, EXIF-очистка их **не удалит** — это проверяется человеком.
- Новые фотографии не синхронизируются с личными фотодневниками других телефонов. Общая лента показывает только явно отправленные, одобренные фото; чат и точная геолокация отсутствуют.
- Проверьте правила удаления информации и согласия для своей аудитории и юрисдикции до публичного запуска.
